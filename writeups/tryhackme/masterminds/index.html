Masterminds: Threat Hunting & Network Traffic Analysis

I investigated three Finance endpoints from PCAP data, using Brim and Suricata to identify payload downloads, recurring C2 patterns and the evidence supporting two malware-family assessments.

Goal: Separate the three infections, document the network evidence for each one and avoid treating reputation results as proof on their own.

1. Scenario

The dataset contained traffic from three compromised Finance machines. I handled each PCAP as a separate case, beginning with HTTP downloads and DNS activity, then pivoting into Suricata alerts and threat-intelligence lookups. The lab suggested phishing and removable media as possible entry points, but the PCAPs were stronger for proving delivery and C2 than for proving the original user action.

2. Investigations: infection1.pcap

Host 192.168.75.249 requested catzx.exe from hdmilg.xyz over cleartext HTTP. Traffic to several unusual domains followed soon afterward, including cambiasuhistoria.growlab.es and gocphongthe.com. The sequence was more useful than any single domain: executable download first, then repeated outbound communication.

One response returned 404 Not Found but still carried 46,456 bytes. I did not treat the status code as benign because the response body was large enough to contain configuration data or another payload. Status, size, content type and surrounding requests need to be reviewed together.

DNS Traffic Analysis

I then checked DNS activity from the same endpoint for domains contacted around the download.

DNS logs showed the same host repeatedly resolving a small cluster of domains. cab.mykfn.com and ie-best.net had the highest query counts. Frequency did not prove C2 by itself, but the timing after catzx.exe made them useful hunting pivots.

During analysis of outgoing HTTP connections, an unusual communication pattern was observed directed toward bhaktivrind.com. The infected endpoint made a GET request to the URI /cgi-bin/JBbb8/, resulting in a 500 Internal Server Error with a response body of 0 bytes.

A server error can be ordinary, so I kept two explanations open instead of assigning intent from the status code alone:

  • The site may have been compromised and used as temporary infrastructure.
  • The path may have expected a specific header or token and rejected the observed request.

www.letscompareonline.com was flagged as malicious by 7/91 security vendors.

cambiasuhistoria.growlab.es was flagged by 8/91 security vendors.

Assessment: True positive — high severity.

192.168.75.249 downloaded an executable and then communicated with a cluster of suspicious domains. The unusual error responses were retained as supporting network artifacts, not presented as proof of a specific evasion technique.

Recommended Actions:

  • Immediately isolate the host from the corporate network.
  • Block all identified C2 domains and IPs at the perimeter firewall.
  • Perform full system reimage.

3. Investigations: infection2.pcap

For 192.168.75.146, the traffic separated naturally into payload delivery and post-download communication:

  • Payload delivery: HTTP GET to hypercustom.top/jollion/apines.exe, resolved to 45.95.203.28.
  • Post-download traffic: repeated HTTP POST requests to 5.181.156.252:80 with a bare IP in the Host header.

I compared the HTTP sequence with Suricata alerts to check the malware and delivery hypotheses.

The IDS alerts occurred at the same time as the download from 45.95.203.28, adding another data source to the HTTP evidence. The useful signatures were:

  • Suspicious Firesale gTLD EXE DL with no Referer: This confirms the automated, script-driven nature of the apines.exe download.
  • Suspicious User-Agent (AutoHotkey): supported an AutoHotkey-based loader or downloader. It did not, by itself, prove that removable media was the entry point.

The OSINT pivot associated the payload with RedLine Stealer. I recorded that as a family assessment supported by reputation data and the POST pattern, not as attribution to a specific operator.

Assessment: True positive — critical severity.

The host downloaded apines.exe and made repeated POST requests to a hardcoded IP. Because the capture did not show the decoded POST contents, I treated data theft as a serious risk rather than claiming exactly what was exfiltrated.

Recommended Actions:

  • Urgent host isolation.
  • Mandatory and immediate password rotation for the affected user across all corporate and financial platforms.
  • Revoke all active session tokens for the compromised user.

4. Investigations: infection3.pcap

The third capture covered 192.168.75.232.

The request pattern looked automated and used several fallback domains:

  • Sequential Payload Retrieval: The host systematically issued HTTP GET requests to download sequentially named executables (/s/1.exe through /s/5.exe).
  • Fallback Infrastructure: To ensure successful delivery, the malware cycled through multiple suspicious Russian TLDs acting as mirror servers: xfhoahegue.ru, afhoahegue.ru, and efhoahegue.ru.

The repeated /s/VNEW=1 requests across these domains are consistent with automated check-ins. I retained the pattern as a C2 lead alongside the download and reputation evidence.

DNS also contained expected Windows noise such as wpad.local and isatap.local, but the host queried many pseudo-random .local names, including hxbhaelzrcmf.local, vrahsvtwl.local and xcpthyukbep.local. I marked this as anomalous internal discovery activity, not confirmed lateral movement.

All automated GET requests to the malicious .ru domains utilized the exact same, hardcoded User-Agent string:

Mozilla/5.0 (Macintosh; Intel Mac OS X 10.9; rv:25.0) Gecko/20100101 Firefox/25.0

The User-Agent claims macOS while the requests retrieve Windows executables. I treated that inconsistency as supporting context, rather than evidence of the endpoint operating system by itself.

A threat-intelligence pivot associated efhoahegue.ru with Phorpiex/Trik infrastructure. The family assessment matched the multi-payload download pattern, but the PCAP remained the primary evidence for the compromise.

Assessment: True positive — high severity.

The host downloaded 1.exe through 5.exe from rotating .ru domains and reused a fixed macOS User-Agent for Windows payloads. The random .local queries justified a wider hunt across internal DNS.

Recommended Actions:

  • Isolate the host immediately to prevent lateral movement.
  • Hunt for .local DNS queries across the broader network to identify if lateral movement was successful.
  • Reimage the machine.

5. What changed my assessment

The assessments combine the download sequence, response characteristics, DNS, IDS alerts and reputation lookups. The unusual error responses and User-Agent remain supporting observations.

  • Behavioral anomalies:
    • Massive HTTP payloads (46KB) masquerading as benign 404 Not Found errors.
    • Direct-to-IP Command & Control communications bypassing DNS resolution.
    • Spoofed, outdated macOS User-Agents requesting Windows .exe executables.
  • Correlation: HTTP downloads, DNS patterns and Suricata alerts supported one another, while threat-intelligence results remained enrichment rather than primary proof.
