Boogeyman 3: Reconstructing an Intrusion in Elastic

I used Elastic and Sysmon telemetry to follow one phishing attachment across two workstations and a domain controller. The useful part of the room was not finding isolated answers; it was proving how each event led to the next stage of the intrusion.

Data source
Elastic / Sysmon
Initial host
CEO workstation
Second host
WKSTN-1327
Key techniques
HTA, Rundll32, WinRM
Outcome
Domain compromise

Case summary

The incident began with a finance-themed email sent to an executive. The attachment looked like a PDF, but Windows treated it as a disk image. Inside was an HTA file that launched through mshta.exe, copied a second-stage payload into the user profile and executed it with rundll32.exe.

From that point, the attacker created a scheduled task, contacted 165.232.170.151:80, abused fodhelper.exe for elevation, downloaded credential tooling and moved to WKSTN-1327 through PowerShell Remoting. Later events showed activity against DC01.quicklogistics.org and a final ransomware download. The available evidence proved staging, but not that encryption actually ran.

AssessmentTrue positive. The initial workstation, a second workstation and the domain controller all required containment and credential reset.

Scope and evidence

I limited the time range to 29–30 August 2023, then worked mainly with process name, parent process, command line, host, user, PID and destination network fields. Parent-child relationships were the fastest way to separate normal Windows binaries from malicious use.

Initial access and execution

The email supplied context, but it did not prove execution. The first strong endpoint evidence was the mismatch between the document-looking name and the mounted image, followed by the HTA handler starting from the mounted drive.

File Explorer launched the HTA handler, which tied user interaction to code execution. The child activity then copied review.dat to a writable local path and passed it to rundll32.exe. A data extension does not make a file harmless when the command line explicitly loads it as executable content.

Persistence, network traffic and elevation

The next reliable pivot was a scheduled task named Review. Its name matched the document theme, but its action pointed back to the staged payload. Outbound telemetry then connected the same chain to repeated HTTP traffic at 165.232.170.151:80.

Later, fodhelper.exe appeared in the parent chain for hidden PowerShell. In this timeline it was not normal administration: it followed payload execution and persistence, and preceded credential-focused activity. I treated that sequence as a UAC-bypass pattern rather than relying on the process name alone.

Credential access

PowerShell downloaded Mimikatz, after which the logs showed credential reuse consistent with pass-the-hash activity. The important distinction was that a download alone only proved tool transfer; the later authentication and remote-execution events showed that credentials were actually used.

Lateral movement and domain activity

The attacker read an automation script from a remote share, obtained another credential and targeted WKSTN-1327. On that host, PowerShell ran under wsmprovhost.exe, which aligned with Windows Remote Management. This gave me evidence on both sides of the movement: the command from the source host and the remoting process on the destination.

Subsequent events reached the domain controller and showed DCSync-related activity. At that point the scope was no longer a single infected workstation. A final executable was downloaded afterward; because the logs shown in the room did not prove encryption, I recorded it as ransomware staging rather than a completed impact event.

Detection ideas

process.name: "mshta.exe" and process.parent.name: "explorer.exe"
process.name: "rundll32.exe" and process.command_line: "*.dat*"
process.name: "powershell.exe" and process.parent.name: "fodhelper.exe"
process.name: "powershell.exe" and process.parent.name: "wsmprovhost.exe"
process.command_line: "*mimikatz*"
process.command_line: "*ransomboogey.exe*"

These are hunting starting points rather than production-ready rules. They should be tuned with path, user, host and allow-list context before deployment.

Conclusion

The strongest evidence came from correlation: a document-looking attachment, HTA execution, Rundll32 staging, scheduled-task persistence, outbound traffic, credential reuse and remoting telemetry on the destination host. Keeping “observed” separate from “likely” also mattered; the logs showed a ransomware download, but not the encryption event itself.
