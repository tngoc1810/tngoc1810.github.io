What I wanted to solve

A rule can match a suspicious command without proving that a payload ran. A failed logon does not prove access. Matching an IP address does not always identify a process. And an asset with no alerts may simply have no useful telemetry.

I wanted the system to keep those distinctions visible. The implementation brings together acquisition, source-scoped detection, process reconstruction, packet inspection, analyst decisions and a verified handoff. It is designed around a laptop with 8 GB RAM, with no VM or Docker required for the core.

From source to reviewable decision

Windows logs→Archive + SQLite→Detection + case review→Verified handoff

Windows acquisition preserves source hashes, original records and timestamps. SQLite holds normalized evidence and operational state. Detections retain references back to the events that triggered them; analyst decisions use revisions and an audit history.

PCAP analysis follows a separate bounded path for packet anchors, TCP reconstruction and protocol observations. Approved endpoint sources provide candidates for attribution. Readiness reads an approved operational snapshot and checks telemetry requirements against asset and service context.

Loki and Grafana are optional native components for delivery and visualization. SQLite remains the local evidence and workflow store.

What is implemented

Evidence acquisition

EVTX exports and polling of existing Windows channels, source byte hashes, original XML, cursors and gap/reset diagnostics. Transactional JSONL ingestion preserves physical-line anchors.

Detection & correlation

Nine Windows rules, three offline authentication hypotheses and one explainable multi-step chain. Live scheduling covers the event rules and AUTH-001; the other investigation steps are offline.

Process & PowerShell investigation

Source-scoped process/session relationships, explicit missing or conflicting links, eight SQL hunts, script-fragment reconstruction and bounded decode. AST analysis parses text without executing it.

Packet analysis

Classic PCAP parsing, bounded TCP reassembly, DNS associations, HTTP framing/body hashes and TLS SNI. Network heuristics create review leads while preserving ambiguous endpoint candidates.

Operational workflow

A durable outbox with leases, retry/backoff and dead letters. Analyst ownership, revision checks, decision history, reviewed export, snapshot and restore keep operations inspectable.

Readiness & handoff

Approved assets and sources, required-field checks, timing and freshness diagnostics, open alerts and review deadlines. v6.1 verifies the report bundle against an independently retained manifest digest.

Eight cases, different evidence boundaries

The collection mixes public artifacts with controlled constructed scenarios. I label them separately so a regression fixture is not mistaken for a real incident capture.

  • 01
    Mshta and scheduled-task activity ↗

    Eight public Sysmon records; an escalation lead, with no claim that a requested task executed repeatedly.

  • 02
    Authentication activity ↗

    3,561 public failed-logon records and a separate credential-use supplement. Failed attempts are not proof of successful access.

  • 03
    A PowerShell string that looked like execution ↗

    Public PowerShell records distinguish quoted or printed script text from observed download or execution.

  • 04
    Context-aware tuning ↗

    Constructed records test exact-match annotation while retaining variations for analyst review.

  • 05
    Session and process reconstruction ↗

    2,511 constructed records across three approved sources; linked process activity, noise and missing or conflicting relationships.

  • 06
    Public HTTP and DNS captures ↗

    Two independent captures totaling 81 packets. Protocol examples are kept separate from an attack verdict.

  • 07
    Network attribution under uncertainty ↗

    17 inert packets, TCP reconstruction and two endpoint candidates. Attribution remains open when the evidence does not select one process.

  • 08
    Telemetry and service readiness ↗

    12 constructed records, two assets and five telemetry requirements reveal missing fields, clock issues and an unmapped host.

Evidence that the implementation was checked

The v6.1 handoff records 170 passing tests on local Python 3.11 and 3.12, with all seven CI jobs passing. The 19 verifier tests cover strict JSON, bounded inputs, report consistency and modified-bundle rejection. Four altered copies were also rejected through the actual CLI.

Operational validation includes a controlled Loki recovery after an actual HTTP 503, with 19 unique event UIDs verified after delivery. Packet checks include an independent parser comparison; release artifacts are checked against retained digests and source inventories.

Design decisions and practical limits

Keep the core small enough to inspect

Python standard library and SQLite make the core reproducible without a large lab stack. Optional native Loki/Grafana provide a backend exercise, while the local workflow remains useful on its own.

Preserve uncertainty instead of hiding it

Delivery is at least once, so an uncertain acknowledgment can produce a duplicate. Hashes and audit chains support consistency checks but do not authenticate a user or establish trustworthy acquisition by themselves. Service readiness is a report run, not a continuous production monitor.

Scope of the published work: a single-workstation lab, with public and constructed investigation evidence plus a separately labeled historical native-collection proof. It does not implement fleet-wide collection, enterprise IAM/RBAC, automated containment or a production SIEM deployment. The 8 GB figure is a design target, not a measured peak-memory guarantee.

What the project helped me practice

Windows event interpretation, SQL investigation, process/session reasoning, TCP and application protocols, defensive Python, durable queues, state transitions, negative testing, reproducible CI and writing a handoff another analyst can check.
